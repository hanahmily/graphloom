GraphLoom

You already let AI review your contributors' pull requests and draft fixes for your issues, and you still re-check every line it gives you.

What I was missing was AI output that comes with proof I can check in a minute, instead of claims I have to redo.

GraphLoom runs coding agents (Claude Code, Codex or Pi, with your own logins, on your machine) through a fixed process, and it only hands you a result once the evidence for it has been checked. You write the process as an executable TypeScript graph.

Write a graph in TypeScript. Let the loom run its agents.

Get started GitHub

Linux only. Runs locally on your machine with your own Claude Code / Codex / Pi logins. No hosted service.

How a run works

A run executes one task in an isolated Git worktree. The graph fixes the stages; executors do the jobs; validators decide what counts. The supervisor handles failures, and the operator makes the calls that need a human.

Graph
A TypeScript plugin that defines the stages of a job (for example Fix → Review), what each stage must prove, and how to route. The graph is code, not a prompt list.
Run
One execution of a task (task.yaml) in an isolated Git worktree, with pinned inputs, recorded evidence and finite budgets: agent calls, jobs, time.
Receipts
A stage is accepted only when validators check the evidence. Agent claims alone don't count.
Supervisor
One recovery agent per run. It investigates failures, can repair the plugin with tested changes, and re-enters the graph. The stages and required outcomes stay fixed.
Executors
Sandboxed workers that do jobs: coding agents, commands (build, test), GitHub reads and writes.
Operator
You, in the loop by design. Runs stop and ask when a human decision is needed. Nothing is pushed or posted unless you enable it.

Two real runs

Recordings of runs that happened, shortened: commands and output are quoted from the run's state and the pull requests it produced (long lines are cut with "…"; the times on the right are real).

Two graphs ship with it

Use them as they are, or read them as examples of how to write your own.

issue-fix

issue → local branch

Fixes an issue test-first and hands you a branch with a ready pull-request description. It does not push; opening the pull request is yours to do.

  1. Issue
  2. Plan
  3. Regression testREDmust fail first
  4. Fix
  5. Test passesGREEN
  6. Independent review
  7. Local branchwith a ready pull-request description

pr-review

pull request → one review

Reviews an incoming pull request in two rounds and posts one COMMENT review whose first line is the verdict. Posting needs a GitHub token you configure for the run.

  1. Round 1
  2. Neutral change report
  3. Questions and answersFirst: “Is this change necessary?”, checked against the project's design principles.
  4. Round 2
  5. Reviewerscorrectnessmaintainabilitysecurity
  6. Independent verifieron a different harness, confirms each finding
  7. One COMMENT reviewfirst line is the verdict

Why it's different

GraphLoom treats a multi-agent job as a process you can read, bound and check.

01

Graphs are code

The process is a TypeScript plugin: the stages, what each must prove, and how to route. Not a prompt list.

02

Evidence over claims

A stage is accepted only when validators check the recorded evidence. An agent saying it is done is not a receipt.

03

Recovery, not give-up

A supervisor investigates failures, can repair the plugin with tested changes, and re-enters the graph. Stages and required outcomes stay fixed.

04

Bounded and inspectable

Finite budgets for agent calls, jobs and time. Follow a run with graphloom watch; look inside it with graphloom inspect.

Quickstart

Linux, with Claude Code, Codex or Pi already logged in on your machine. A release bundles its own Node.js; the local build needs any Node on PATH to fetch the pinned runtime, plus git, tar, gzip, xz and sha256sum.

  1. Install

    Installable releases are local builds for now: none is published yet. Build one from a clone and install it. Use the version in the root package.json, currently 0.0.0. --unsigned makes a development build, which is right for your own machine.

    git clone https://github.com/hanahmily/graphloom.git
cd graphloom
scripts/release.sh build 0.0.0 --unsigned
scripts/install.sh --from release-out/0.0.0/graphloom-0.0.0-linux-x64.tar.gz

  2. Set up and check

    The installer runs graphloom doctor once; run these to configure and review.

    graphloom setup
graphloom doctor

  3. Link the graph

    Use a working directory of your own, not the target repository. A task finds its graph under plugins/<graph> beside it; link the installed version's real path, never current. Use plugins/pr-review the same way for reviews.

    mkdir -p ~/graphloom-work/plugins && cd ~/graphloom-work
ln -s "$(graphloom version --root)/examples/plugins/issue-fix" plugins/issue-fix

  4. Describe the task

    For pr-review, graphloom task new writes the task and needs --profile: a name looked up in profiles/ beside you and then in the bundle (it ships banyandb), or a path to a JSON file. For another repository, copy a shipped profile and adjust it. For issue-fix, write task.yaml by hand (right) or let the graphloom-run skill write it.

    graphloom task new pr-review owner/repo#123 --repo ./clone --profile banyandb

  5. Run, watch, inspect

    graphloom run task.yaml
graphloom watch <run>    # follow the run
graphloom inspect <run>  # look inside the run

task.yaml, beside plugins/

graph: issue-fix
repo: ./widgets
config: profiles/widgets.json
request: "Fix acme/widgets#42."

graph selects the plugin, repo the repository to work on (relative to this file), config a copy of one of the graph's shipped profiles, adjusted, and request what to do. examples/issue-fix-graphloom-task.yaml in the repository is a working example.
